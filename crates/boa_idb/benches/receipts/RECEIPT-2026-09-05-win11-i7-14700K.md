## Misses → M7-B follow-ups (profile required before optimizing)

1. **FS `put` batch collapse (F1).** 10.4 s per 10k batch (~1 ms/put) vs
   14 µs/put at 200-record smoke scale: per-transaction cost grows
   superlinearly with batch size. Suspects: WAL frame assembly, `rpds` map
   churn, or savepoint scaling. Criterion profile + flamegraph in M7-B.
2. **SQLite 1M cursor scan cliff (F2).** Measured at **847 records/s**
   over 1180.9 s (evidence: `raw-scan-1m-sqlite-20260905.log`; earlier
   shared-fixture estimate in `raw-bench-1m-scan-cliff-20260905.log`).
   475× slowdown for 50× rows vs the 20k diagnostic rate ⇒ severely
   superlinear paging (suspected `LIMIT`/`OFFSET` re-scan). Keyset
   pagination is the M7-B candidate. No optimization was done in this
   rework (P1-2 forbids it); only harness/receipt changed.
3. **JS↔core overhead 80 µs vs 15 µs (F3).** The measured section includes
   script eval, two job drains and a result readback per iteration — an
   upper bound, not a pure pump cost. M7-B must break the cost down
   (parse vs pump vs dispatch) and profile.
4. **SQLite 1M open 310 ms vs 200 ms (F4).** 1.55× over; profile open path
   (page cache warmup / index build) in M7-B.
5. **FS strict commits 212/s (F5).** Above target but marginal; watch as a
   regression canary, no action unless M7-B profiling implicates fsync
   batching.

No target was weakened and no benchmark deleted: the normative/diagnostic
boundary is explicit (`scan-1m` defaults = 1M normative; criterion
`cursor_scan_<N>` = diagnostic). The 20k ids carry their record count and
are excluded from the target counts above.
