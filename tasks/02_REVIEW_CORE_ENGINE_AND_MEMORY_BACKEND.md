## 3. Детальный аудит реализованных компонентов

### 3.1. Планировщик транзакций (`boa_idb_core::engine::scheduler`)
- **FIFO-справедливость и защита от голодания (`R7.2.2`):** Реализован строгий алгоритм `can_start`, который проверяет конфликты не только с уже выполняющимися транзакциями, но и с более ранними в очереди. Если ожидающая `ReadWrite` транзакция заблокирована, последующие конфликтующие `ReadOnly` транзакции не стартуют в обход нее.
- **Эксклюзивность `VersionChange` (`R7.2.1`):** Запуск `VersionChange` эксклюзивно блокирует базу; ни одна другая транзакция не стартует до ее завершения.
- **Параллелизм `ReadOnly`:** Множественные `ReadOnly` транзакции к одним и тем же хранилищам выполняются параллельно без взаимных блокировок.

### 3.2. Конечный автомат открытия и версионирования (`boa_idb_core::engine::open_queue`)
- Реализованы все состояния FSM очереди открытия (§5.1, §5.3): `Idle`, `WaitingForConnections`, `RunningUpgrade`, `RunningDelete`.
- Корректно генерируются действия:
  - `OpenConnection` — при совпадении версии или `version = 0`;
  - `FailOpen` с `IdbError::Version` — при запросе версии меньше текущей;
  - `SendBlocked` — при необходимости апгрейда/удаления, если есть открытые соединения;
  - `StartUpgrade` / `StartDelete` — после закрытия всех блокирующих соединений.

### 3.3. Генератор ключей с откатом (`boa_idb_core::engine::keygen`)
- Диапазон ограничен значением $2^{53}-1$ (`9_007_199_254_740_991.0`). При переполнении возвращается `IdbError::Constraint`.
- Реализована функция `possibly_update(key)`: при вставке явного ключа $\ge current$ генератор перемещается на $\lfloor key \rfloor + 1$.
- Реализован стек точек сохранения (`begin_request`, `commit_request`, `rollback_request`): при откате savepoint запроса значение генератора ключей строго восстанавливается.

### 3.4. Операции над хранилищем и индексами (`ops_store`, `ops_index`)
- Автоматическое определение первичного ключа: извлечение по `keyPath`, генерация через `KeyGenerator` при `autoIncrement`, проверка недопустимости явного ключа при наличии `keyPath`.
- Синхронизация индексов:
  - Поддержка `multiEntry`: массивы ключей распаковываются в отдельные индексные записи.
  - Проверка уникальности (`unique`): попытка вставить дублирующий индексный ключ возвращает `IdbError::Constraint`.
  - Удаление индексных записей по первичному ключу (`delete_by_primary`).

### 3.5. In-Memory бэкенд (`boa_idb_memory`)
- Структура на базе `BTreeMap` для записей хранилищ и индексов.
- Изоляция транзакций через разделение локального состояния (`pending_records`, `pending_index_entries`, `pending_key_generators`) и зафиксированного (`storage_state`).
- Реализован стек Undo-логов (`UndoOp::RestoreRecord`, `UndoOp::RestoreIndex`, `UndoOp::RestoreKeyGen`):
  - `begin_request()` создает новый фрейм стека;
  - `commit_request()` фиксирует изменения запроса;
  - `rollback_request()` откатывает изменения запроса до предыдущего состояния.

## 4. Замечания и рекомендации к доработке (Action Items)

Перед переходом к этапу **M3 (JS-биндинги)** рекомендуется выполнить следующие точечные улучшения:

### Замечание 1. Доработка `scan`, `count` и `delete_range` в `MemoryTxn`
В `crates/boa_idb_memory/src/txn.rs` методы `scan`, `count` и `delete_range` содержат заглушки:
- **Рекомендация:** Реализовать сканирование диапазона `EncodedRange` по объединенному представлению `BTreeMap` (зафиксированные данные + `pending_records`), собирая записи в `MemoryCursor`. Это обеспечит полноценную работу курсоров и операций `getAll`/`count` на memory-бэкенде в связке с JS-биндингами.

### Замечание 2. Инжекция сгенерированного ключа в `ScValue` при `autoIncrement`
В `ops_store::determine_key`:
- При генерации нового ключа для хранилища с `keyPath` и `autoIncrement` сгенерированный ключ должен быть инжектирован обратно в `value` через `store_meta.key_path.inject(value, &key)`.
- **Рекомендация:** Передать `value: &mut ScValue` в `determine_key` и вызывать `inject` сразу после генерации ключа, чтобы сохраняемый объект содержал свой первичный ключ в теле.

### Замечание 3. Добавление `differential_model_tests.rs`
- **Рекомендация:** Добавить тест на основе `proptest`, прогоняющий 10 000 случайных операций (`Put`, `Get`, `Delete`, `Rollback`) параллельно на `MemoryTxn` и эталонном `HashMap`, подтверждая совпадение результатов.
